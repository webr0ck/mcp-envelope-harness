# The verifier is published from the reference implementation's repository and
# pulls in cryptography and jcs (RFC 8785 canonicalisation) itself.

# KNOWN GAP: it FLOORS them (cryptography>=44, jcs>=0.2.1) rather than pinning. The
# signer and the verifier must canonicalise identically, so a jcs skew between the
# two sides is an authenticity failure that surfaces as content_hash_mismatch - it
# looks exactly like an attack. Nothing here prevents that today.
#
# KNOWN GAP: this tracks a branch, not a tag or commit. A clone today and a clone
# next month are not the same verifier, and a compromise of that repo replaces the
# security-critical component here silently. Pin it to a tag before relying on this
# for anything real. See "Open problems" in the article.
